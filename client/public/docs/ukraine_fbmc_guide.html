PyPSA Ukraine FBMC — User's Guide

Everything you need to configure, run and interpret the flow-based market coupling (FBMC) model of the European day-ahead electricity market with a high-resolution Ukrainian network — from the model's web interface.

← Back to the model overview

1. About the model

Flow-based market coupling (FBMC) is the capacity-allocation method used in most of continental Europe's day-ahead market: instead of fixed cross-border exchange limits, it computes an hourly flow-based domain — a set of constraints on zonal net positions derived from the physical grid. The market is then cleared as a single optimization that respects that domain, producing zonal day-ahead prices and cross-border flows.

This model couples a high-resolution, nodal PyPSA-Eur network of Ukraine and Moldova to the rest of Europe, aggregates both sides into country bidding zones, and clears the coupled zonal market with Gurobi (HiGHS fallback) for any window of the 2023 reference year, with optional N-1 security constraints. The methodology and the underlying code are released as the open-source pypsa-fbmc project; this platform runs their implementation as a web service.

What you get: hourly zonal day-ahead prices, zonal net positions (exports/imports), generation mix, load shedding, the binding critical network elements that shaped prices, window KPIs, and CSV downloads of everything.

2. Quick workflow

The model's left-hand menu has four steps, in order:

  1. Configure — pick a scenario, a time window inside 2023, security level (N-0/N-1), a GSK strategy, a base case and the value of lost load. Save your configuration under a name.
  2. Run — give the run a name and press Run Ukraine model. Progress streams live into the console; you also receive an email when the run completes (or fails).
  3. Results — KPIs, charts and per-file downloads for any successful run (see section 5).
  4. History — all past runs; reopen or re-download any of them.

Typical durations on the platform's compute box: N-0 ≈ 3 minutes per window day, N-1 ≈ 24 minutes per window day (measured). Long windows are solved automatically in chunks (up to 7 days per chunk for N-0, 1 day for N-1) and the results are stitched back together.

GSK strategies in one line each

  • P_NOM — each node responds proportionally to its generation capacity (p_nom). The default on this platform.
  • BUS_P — proportional to the node's current power injection in the base case.
  • CURRENT_GENERATION — proportional to current generation output.
  • MERIT_ORDER — generators respond in merit order (cheapest first).
  • ADJUSTABLE_CAP — only dispatchable carriers (gas, coal, lignite, oil) respond, proportional to their adjustable capacity.
  • ITERATIVE_UNCERTAINTY — Monte-Carlo sampling of wind uncertainty, refined iteratively (slow).
  • ITERATIVE_FBMC — GSK refined iteratively from FBMC outcomes, starting from BUS_P (slow).

4. Running a window

  1. Open Run, type a Run name (required — it labels the run in your history) and press Run Ukraine model.
  2. The live output console below the button streams progress line by line. Long windows show [chunk k/n] prefixes — the solver works through your window chunk by chunk and stitches the results automatically.
  3. When the run finishes you get an email (success or failure), and the run appears under Recent runs and in History. Open the Results tab to explore it.

What to expect

  • Runtime: ≈ 3 min per window day for N-0, ≈ 24 min per window day for N-1 (the Configure tab shows a live estimate). A 7-day N-1 window therefore takes several hours.
  • One model run at a time: the platform allows a single heavy run globally. While your Ukraine run solves, launching other models (and vice versa) is refused with a “blocked by another run” message — just try again once it finishes.
  • Duplicate reuse: if a run with an identical configuration already succeeded, the platform returns the stored results immediately and marks the run (reused) in history — no re-solve.
  • Safety rails: runs have a 6-hour budget and a RAM guard; if either is exceeded the run is killed cleanly, marked failed in your history, and an email is sent. Shrinking the window or switching N-1 to N-0 fixes overruns.
Window format matters: timestamps look like 2023-06-01 08:00:00 — hour precision, both ends inclusive, inside 2023. The most common rejected run is a window ending at midnight (00:00:00) or extending past 2023-12-31 23:00:00; end the last day at 23:00:00 instead.

5. Results & how to interpret them

The Results tab summarizes a successful run as KPI cards and charts (zonal price curves, a shedding timeline when shedding occurs, net-export and welfare comparisons between Ukraine and the rest of Europe, and the table of binding critical network elements), with a download button for every result file.

The result files, one by one

FileContainsHow to read it
market_prices.csv Hourly day-ahead price per bidding zone (EUR/MWh). Prices are equal across zones whenever no CNEC binds; a price split means congestion — see which branch in cnec_binding.csv.
net_positions.csv Hourly net position per zone (MW). Positive = the zone is a net exporter in that hour. Summing over the window (and multiplying by 1 h) gives net exported energy.
generation_mix.csv Hourly dispatch by zone and carrier (MW). The generation stack behind the prices — e.g. how much of Ukraine's hours are hydro, nuclear, solar, wind.
load_shedding.csv Hourly unserved load per zone (MW). Zero in a healthy clearing. Any positive value marks an hour in which demand could not be delivered inside the flow-based domain — the hours the grid (not the market) is the binding constraint.
cnec_binding.csv Critical network elements (branch + outage) that bound the domain. Each row shows how many hours the element bound and its maximum shadow price (EUR/MWh) — the congestion cost of that line limit. This table explains the price splits.
kpis.json Window-level and per-zone KPIs: mean/max prices, load and generation totals, net import, shed MWh, consumer expense, producer revenue and congestion-rent contribution. The quick-scan summary of a window; compare runs by diffing these numbers.
run_meta.json The effective configuration, per-chunk timings and peak memory. Provenance — what exactly produced these numbers, and how hard it was.

Reading the welfare split

The KPI welfare terms decompose the market outcome per zone: consumer expense is load × price (what demand pays), producer revenue is generation × price (what supply earns), and the congestion-rent contribution is the value captured by the flow-based domain's binding constraints. Comparing Ukraine/Moldova against the rest of Europe shows who benefits from coupling in the chosen window.

Comparing configurations

  • N-0 vs N-1: switching security on adds contingency constraints — expect a smaller flow-based domain, lower cross-border capacity, larger price splits and (in extreme scenarios) more shedding. (Reliability margins: N-1 → 0.1, N-0 → 0.5.)
  • base vs red vs redload: the reduced-fleet scenarios show how a damaged Ukrainian power system leans on imports, sheds load when the domain cannot deliver, and decouples from European prices.
  • VOLL: lowering the value of lost load reveals scarcity hours earlier (shedding appears at lower prices) — useful for stress-testing, but it also lowers the model's price ceiling.

6. Tips & troubleshooting

  • Start small. A single reference day (the default window) validates your setup in minutes; extend to a week once it behaves as expected.
  • Validation errors are reported per field — the message names the exact rule violated (window bounds, the 7-day cap, hour precision, VOLL range), so fix the named field and re-save.
  • “Blocked by another run” means some model (possibly another user's) is currently solving on the shared compute box. Nothing is lost — re-launch when it clears.
  • A failed run does not block a retry — failures are kept in History with their last output for diagnosis, and the same configuration can be relaunched immediately (identical successful runs are the only ones reused).
  • Where results live: every run keeps its files on the platform; History re-opens and re-downloads them at any time.
